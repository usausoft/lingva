# Configuration

Lingva's portable CLI contract is `lingva.config.yaml`. It is declarative and
works unchanged in JavaScript, Python, and CI. JavaScript framework runtimes may
also use `lingva.config.ts` when they need typed imports; that runtime adapter
is separate from the language-neutral CLI contract.

## One CLI interface across languages

The executable is always `lingva`. Direct install, npm, and PyPI all launch the
same standalone Rust engine:

| Workflow             | Command        |
| -------------------- | -------------- |
| Initialize           | `lingva init`  |
| Align locale files   | `lingva sync`  |
| CI check             | `lingva check` |
| Download hosted copy | `lingva pull`  |
| Publish local copy   | `lingva push`  |

Remote is the default initialization mode:

```bash
lingva auth login
lingva init --sdk python
```

Use `--platform-url https://stage.lingva.dev` for another Lingva deployment.
Use `--mode local --no-auth` only for an account-free local project. In CI,
authenticate with `auth use-key`, add `--non-interactive`, and pass the explicit
project/API values generated by the project setup page.

The YAML config contains no executable code:

```yaml
projectId: lingva-app
environment: stage
locales:
  - en
  - ru
defaultLocale: en
fallbackLocale: en
translationFiles: .lingva/translations/{locale}.json
apiUrl: https://your-publish-api.lambda-url.eu-west-1.on.aws
apiKeyEnv: LINGVA_API_KEY
```

Keep credentials in the named environment variable, never in this file. The
common contract covers local sync/check and hosted pull/push. Framework runtime
setup remains language-specific because React providers and Python application
lifecycles are different concerns.

For `sync`, `check`, `pull`, and `push`, the config path is optional. Lingva reads
`lingva.config.yaml` from the current project root by default. Pass a path only
when the config has a different name or location.

Do not maintain equivalent YAML and TypeScript files in the same directory.
The zero-argument commands intentionally prefer YAML. Choose YAML for the
portable CLI workflow; choose TypeScript when the JavaScript runtime imports
the config directly.

Install the CLI before using the commands in this guide:

```bash
curl --proto '=https' --tlsv1.2 -LsSf https://unpkg.com/@lingva/cli@latest/lingva-installer.sh | sh
```

The next release separates the Python CLI installer from the application runtime:

```bash
python -m pip install lingva-cli
```

Rust developers can compile the published crate directly:

```bash
cargo install lingva
```

The standalone installers remain the recommended route for customers because
they install a checksummed prebuilt binary and require no language toolchain.

The Rust CLI implements all 23 customer commands, including extraction,
code generation, metadata, authoring, and studio. npm and PyPI are checksum-verifying launchers, not
separate implementations. Framework scaffolding is native Rust behavior.
These commands require CLI 0.1.4 or newer; verify with `lingva --version`.
See the [complete command reference](./cli.md) for examples, policy options,
error handling, and adapter compatibility. npm alone evaluates executable
JS/TS configs through its temporary portable-config bridge.

Run `lingva update` to check the stable release for the installation channel.
Python uses PyPI, Cargo uses crates.io, and standalone/npm/Homebrew use stable
npm engine metadata. It reports a channel-specific upgrade command without
changing the installation. Use `--channel` to override automatic detection.

For the local-first workflow, that config should stay declarative. Users should
not need to import every locale file manually.

Create the portable YAML config explicitly:

```bash
lingva init --sdk python
```

For React and Next.js apps, you can instead scaffold a typed TypeScript runtime
adapter under `.lingva/generated/runtime.ts` together with the first provider
wrapper. Portable YAML remains the sole root CLI owner; the scaffold does not
create an equivalent `lingva.config.ts` beside it:

```bash
pnpm lingva init --sdk react
pnpm lingva init --sdk next
```

For local-mode projects that should protect translation state in pull requests,
ask init to add a GitHub Actions workflow:

```bash
pnpm lingva init --mode local --no-auth --ci github
```

You can inspect the generated files first:

```bash
pnpm lingva init --dry-run --format text
```

With `--ci github`, local-mode init creates
`.github/workflows/lingva-local.yml`. The workflow installs the checksummed
standalone binary and runs `lingva check` for pull requests without requiring
Node.js or Python.

## Local Mode

Use local mode when translations live in your repository.

Example scaffold:

```ts
import { defineLingvaConfig } from '@lingva/core';

const lingvaConfig = defineLingvaConfig({
  projectId: 'lingva-app',
  locales: ['en', 'ru'],
  defaultLocale: 'en',
  locale: 'en',
  fallbackLocale: 'en',
  translationFiles: '.lingva/translations/{locale}.json',
  generatedProjectFile: '.lingva/generated/project.ts',
  metadataFile: '.lingva/metadata.json',
  delivery: {
    mode: 'local',
    path: '.lingva/translations/{locale}.json',
  },
});

export default lingvaConfig;
```

That config is intentionally small. The locale JSON files are discovered from
the `translationFiles` pattern and the hidden generated project module is
managed by Lingva itself.

Key metadata can stay declarative too. `lingva init` does not create a metadata
file. Run `lingva metadata --output .lingva/metadata.json` and configure
`metadataFile: .lingva/metadata.json` in the portable config. If you add new default
locale keys later, scaffold missing metadata without overwriting existing
entries:

```bash
pnpm lingva metadata lingva.config.yaml --output .lingva/metadata.json
pnpm lingva sync lingva.config.yaml
pnpm lingva check lingva.config.yaml
```

The metadata scaffold starts new keys as `draft` with TODO descriptions. Update
descriptions, tags, translator, and reviewer fields as the copy moves through
your workflow.

CI can verify metadata drift without writing files:

```bash
pnpm lingva metadata lingva.config.yaml --check
```

Local translation files live in the default repository path:

```json
{
  "common": {
    "appName": "Lingva app",
    "welcome": "Welcome"
  },
  "auth": {
    "signIn": {
      "title": "Sign in"
    }
  }
}
```

At runtime, both `common.welcome` and nested resources resolve through the same dot-path contract.

## Translation key contract

Every Lingva integration uses the same flattened translation-key rules:

- at most 200 characters
- letters, digits, dots, underscores, and hyphens only
- the first character must be a letter or digit
- no trailing dot or consecutive dots

For example, `docs.python.getting-started_1` is valid. Keep the key as a short,
stable identifier even when its translated value is a long paragraph. Pricing
and plan quotas count distinct flattened keys, not the number of characters in
their values.

`lingva check` detects invalid keys before publishing. The hosted authoring and
publish APIs enforce the same contract, so JavaScript, Python, CI, and the web
editor cannot create incompatible translation state.

Translation leaves must be strings or non-empty variant arrays. Empty arrays,
numbers, booleans, nulls, duplicate variant IDs, and dotted-key parent
collisions fail before sync or publish instead of being silently discarded.

Lingva also supports variant-rich leaves when one key needs multiple tones or
intonations. In that case, the leaf becomes an array of typed variant objects:

```json
{
  "marketing": {
    "hero": {
      "title": [
        {
          "id": "warm",
          "tone": "warm",
          "text": "Welcome back, {user.name}."
        },
        {
          "id": "bold",
          "tone": "bold",
          "text": "Let us ship today, {user.name}."
        }
      ]
    }
  }
}
```

Runtime lookups still use the same key:

```ts
t('marketing.hero.title', {
  variant: 'bold',
  variables: {
    user: {
      name: 'Nino',
    },
  },
});
```

Lingva validates that non-default locales keep the same leaf contract as the
default locale. If the default locale uses variants for a key, the other
locales must also keep that key as a variant array. Validation also reports
variant drift when a locale is missing a default-locale variant, adds an extra
variant, or changes contract metadata such as `tone`, `mood`, `intonation`,
`label`, or `context`.

## Local Editing Workflow

For now, the intended local-first workflow is:

1. treat the default locale file as the source of truth
2. edit keys there first
3. run `lingva sync`
4. let Lingva add missing keys to other locales without overwriting existing translations

To keep local locale files aligned with the default locale without overwriting existing translations:

```bash
pnpm lingva sync ./lingva.config.yaml
```

That command:

- validates the local config shape
- ensures every target locale contains keys from the default locale
- preserves variant-array structure for keys that use tone/style variants
- reports missing variants, extra variants, and variant metadata mismatches separately
- preserves existing translations
- changes locale JSON only; generated JavaScript project modules import those files

To use the same logic in CI without writing files:

```bash
pnpm lingva sync ./lingva.config.yaml --check
```

For the normal local and CI preflight, prefer the combined check command:

```bash
pnpm lingva check ./lingva.config.yaml
```

That command runs sync in check mode, validates the resulting project contract,
and exits non-zero if either locale files are out of sync or validation crosses
the configured `--fail-on` threshold.

To verify the resulting project contract:

```bash
pnpm lingva validate ./lingva.config.yaml
```

That validation path reads the portable project's locale dictionaries, including
missing keys across locales and contract mismatches
between plain-string and variant-based translation leaves.

For CI that should fail only when the translation contract drifts, use:

```bash
pnpm lingva validate ./lingva.config.yaml --fail-on variant-drift
```

## Remote Mode

Remote `pull` and `push` use optimistic concurrency. Both JavaScript and Python
CLIs keep the last hosted revision and base dictionaries in the gitignored
`.lingva/remote-state.json` file. `pull` three-way merges by translation key;
same-key local and hosted edits fail without overwriting files. `push` fails
with HTTP `409` when the hosted revision moved. Repeating an identical push
returns the existing publish. Use `--force` only when replacing newer hosted
state is intentional.

Use remote mode when bundles should come from Lingva-hosted delivery.

```bash
pnpm lingva auth login
pnpm lingva init --project-id dashboard --api-url "$LINGVA_PUBLISH_API_URL"
```

Example remote config:

```ts
import { defineLingvaConfig } from '@lingva/core';

const lingvaConfig = defineLingvaConfig({
  projectId: 'dashboard',
  environment: 'stage',
  locale: 'en',
  fallbackLocale: 'en',
  apiUrl: process.env.LINGVA_PUBLISH_API_URL,
  apiKey: process.env.LINGVA_API_KEY,
  delivery: {
    mode: 'cdn',
    url: 'https://example.lambda-url.eu-west-1.on.aws/bundles/{projectId}/{environment}/latest/{locale}.bundle.json',
    timeoutMs: 10_000,
  },
});

export default lingvaConfig;
```

Remote mode has two security rules:

- Browser delivery should use a project SDK key scoped only to `delivery:read`;
  the key is an identifier and quota/revocation credential, not a browser
  secret.
- Project-admin keys, publish tokens, and authoring tokens must stay in
  server-only environment variables.

Copy `LINGVA_PUBLISH_API_URL` and the current bundle URL from the target
environment on the project setup page. Hosted environments have dedicated
endpoints, so remote initialization intentionally has no implicit API URL.

Remote HTTP loads time out after 10 seconds by default. Set `timeoutMs` to a
different positive duration when needed. Imperative loads also accept an
`AbortSignal`, for example `client.preload(keys, locale, { signal })`, so an
application can cancel work when its owning request or view is disposed.

The recommended hosted setup flow is:

1. create a Lingva project and open `/app/projects/<project-id>`
2. create the `delivery:read` SDK key in **Consumer application setup**
3. copy the generated wizard command, or its project ID, publish URL, and bundle URL
4. copy the generated `lingva auth login` command for local developer publishing
5. run `lingva check` and `lingva push --invalidate`
6. deploy the app with only read-only delivery values exposed to the browser

`lingva pull` downloads hosted bundles and three-way merges authored values
into the project's locale dictionaries. Configure the publish/delivery endpoint
and a credential with read access first. Same-key conflicts fail before writes;
fallback-only values are not copied into the requested locale. Verify delivery
with the deployed bundle URL and a read-scoped SDK key.

See [Integration Paths](/installation/integration-paths) for the full
copy-pasteable path.

## Using the Same Config Everywhere

```ts
import { createLingvaJsRuntime } from '@lingva/js';
import lingvaConfig from './lingva.config';
import project from './.lingva/generated/project';

export const lingva = createLingvaJsRuntime({
  ...lingvaConfig,
  project,
});
```

React apps can either pass the shared config directly:

```tsx
import project from './.lingva/generated/project';
<LingvaProvider config={{ ...lingvaConfig, project }}>{children}</LingvaProvider>;
```

or, in a browser-only application, preconfigure Lingva once and let
`LingvaProvider` pick it up automatically. These defaults are process-global;
do not use them for request-specific SSR locales or credentials. Pass explicit,
request-owned configuration on servers:

```tsx
import { configureLingvaReact, LingvaProvider } from '@lingva/react';
import lingvaConfig from './lingva.config';
import project from './.lingva/generated/project';

configureLingvaReact({
  ...lingvaConfig,
  project,
});
<LingvaProvider>{children}</LingvaProvider>;
```

or start from the generated wrapper:

```tsx
import { AppLingvaProvider } from './src/lingva/provider';

export function Providers({ children }: { children: React.ReactNode }) {
  return <AppLingvaProvider>{children}</AppLingvaProvider>;
}
```

Next.js projects can use the framework-specific helper generated by:

```bash
pnpm lingva init --mode local --no-auth --sdk next
```

That wrapper uses `createLingvaNextProvider` from `@lingva/next` and can be
mounted from `app/layout.tsx`.

The same browser-only global-default pattern exists for plain JavaScript and
static-site surfaces. Servers should create request-owned runtimes with explicit config:

```ts
import { configureLingvaJs, createLingvaJsRuntime } from '@lingva/js';
import lingvaConfig from './lingva.config';
import project from './.lingva/generated/project';

configureLingvaJs({
  ...lingvaConfig,
  project,
});

const lingva = createLingvaJsRuntime();
```

or use the newer high-level runtime props:

```tsx
<LingvaProvider
  runtime={{
    mode: 'remote',
    apiUrl: process.env.NEXT_PUBLIC_LINGVA_PUBLISH_API_URL,
    apiKey: process.env.NEXT_PUBLIC_LINGVA_API_KEY,
    projectId: 'dashboard',
    locale: 'en',
    fallbackLocale: 'en',
  }}
>
  {children}
</LingvaProvider>
```

Never put private write or management keys in `NEXT_PUBLIC_*` variables. If a
browser app needs authenticated Lingva access, route it through your server and
attach the private token there.

## CLI Auth

For hosted workflows, use browser-based CLI auth instead of pasting tokens into
every command. Lingva customers should copy this complete command from
**Consumer application setup** on their project page:

```bash
lingva auth login \
  --issuer-url https://auth.example.com \
  --client-id lingva-cli
```

The CLI opens the browser, completes an OAuth/OIDC authorization-code flow with
PKCE through `http://127.0.0.1:53682/callback`, and stores credentials in
`~/.lingva/credentials.json` with private file permissions. Register that
localhost callback in the identity provider, or pass `--port` if your provider
uses another allowed callback port. You can also provide explicit endpoints when
the issuer does not follow the standard `/oauth2/*` shape:

```bash
lingva auth login \
  --authorize-url https://auth.example.com/oauth2/authorize \
  --token-url https://auth.example.com/oauth2/token \
  --client-id lingva-cli
```

After login, hosted CLI commands use the saved access token when `--auth-token`
is omitted. Explicit flags and project config still win, which keeps CI and
stage-specific automation deterministic. If the provider returns a refresh
token, Lingva stores the token endpoint and client id alongside the credentials
and refreshes expired access tokens automatically before hosted commands.

That means local reviewer and maintainer commands can stay tokenless after the
first login:

```bash
lingva drafts ./lingva.config.yaml \
  --api-url "$LINGVA_AUTHORING_API_URL" \
  --environment stage

lingva approve ./lingva.config.yaml \
  --draft-id draft_123 \
  --api-url "$LINGVA_AUTHORING_API_URL" \
  --publish-api-url "$LINGVA_PUBLISH_API_URL" \
  --push \
  --invalidate \
  --reason "Approved draft publish"
```

Keep `--auth-token` for CI, break-glass automation, or service-token based
jobs. Do not expose those service tokens to browser code.

Hosted authoring and publish endpoints accept stored CLI bearer tokens only
when the backend has JWT verification configured. With the bundled AWS stack,
the stack configures the Cognito user-pool JWT issuer and app-client checks.
`COGNITO_DOMAIN_PREFIX` separately enables the Hosted UI/OAuth login endpoints;
that hosted domain is not the JWT `iss` value.
The deployment requires `LINGVA_AUTHORING_ALLOWED_GROUPS`,
`LINGVA_CONTROL_PLANE_ALLOWED_GROUPS`, and `LINGVA_PUBLISH_ALLOWED_GROUPS`.
They limit which Cognito groups can use user tokens and fail closed when empty;
service tokens remain available for CI and server-only dashboard automation.

If you deploy the bundled AWS infrastructure with Cognito Hosted UI, set a
stage-specific `COGNITO_DOMAIN_PREFIX` and keep the separate
`COGNITO_CLI_APP_CLIENT_NAME` / `COGNITO_CLI_CALLBACK_URLS` values. The stack
then emits `UserPoolHostedUiIssuerUrl` and `CliUserPoolClientId`, which map
directly to the CLI flags:

```bash
lingva auth login \
  --issuer-url <UserPoolHostedUiIssuerUrl> \
  --client-id <CliUserPoolClientId>
```

The normal web Cognito app client remains separate from the CLI client so local
PKCE loopback callbacks do not need to be registered on browser-facing app
clients.

Maintainers using the bundled infrastructure can print those values directly
from CloudFormation:

```bash
pnpm --filter @lingva/infrastructure-aws auth:env:dev
```

Use `auth:env:stage` or `auth:env:prod` for the matching deployed stage. The
command is read-only and prints shell exports plus the final `lingva auth login`
command.

Useful auth commands:

```bash
lingva auth status
lingva auth logout
```

Device login is available only with a provider that supports device grants.
It does not enable that grant in Cognito. For headless use, provision an
appropriately scoped API key or forward the browser callback safely. With a
device-capable provider:

```bash
lingva auth login \
  --issuer-url https://auth.example.com \
  --client-id lingva-cli \
  --device-url "$DEVICE_AUTH_URL" \
  --device
```

The CLI prints the verification URL and user code, then waits until the browser
approval completes.

## Delivery Artifacts

When you need artifacts for CI, inspection, or hosted delivery:

```bash
lingva bundle ./lingva.config.yaml --locale en --format json --output ./artifacts/lingva-bundle.en.json
```

To generate a manifest plus bundles together:

```bash
lingva publish ./lingva.config.yaml --locale en,de --output-dir ./artifacts/publish
```

To send those artifacts to a hosted Lingva publish endpoint:

```bash
lingva publish ./lingva.config.yaml \
  --locale en,de \
  --output-dir ./artifacts/publish \
  --api-url https://example.lambda-url.eu-west-1.on.aws/
```

To request downstream refresh after publish:

```bash
lingva invalidate ./lingva.config.yaml \
  --api-url https://example.lambda-url.eu-west-1.on.aws/ \
  --source repository \
  --reason "Refresh after merge"
```

To do both steps as one hosted delivery action:

```bash
lingva push ./lingva.config.yaml \
  --locale en,de \
  --output-dir ./artifacts/push \
  --api-url https://example.lambda-url.eu-west-1.on.aws/ \
  --invalidate \
  --source repository \
  --reason "Refresh after merge"
```

For an offline artifact preview, export a normalized project first:

```bash
lingva export lingva.config.yaml --format json --output .lingva/artifacts/plan/project.json
lingva publish .lingva/artifacts/plan/project.json --output-dir .lingva/artifacts/plan
```

The normalized export embeds resources and omits endpoints, credentials, and policies.
Do not add endpoint flags or a hosted `--config` override to the second command.
This writes artifacts locally without publishing to a hosted endpoint.

## What Comes Next

The current local-first workflow is already usable for application development,
but some capabilities remain previews:

- `lingva studio` is an offline JSON editor; export edited locale JSON and apply it with `lingva apply`
- native Swift, Kotlin, and Flutter runtimes are source previews, without built-in authenticated hosted loading
- dedicated Next.js Server Component translation helpers are not implemented

Hosted pull/push, draft approval, and local validation are implemented by the
Rust engine. See the [CLI reference](./cli.md) for command effects and recovery.
