# Next.js Starter

Use `examples/next-starter` to inspect the current Next.js integration in a real
App Router app before wiring Lingva into your own product. The bundled example
runs inside this public monorepo because its dependencies use `workspace:*`.
It is separate from the files generated by `lingva init` in a customer application.

## Scaffold It {#scaffold-it}

Run these commands in the root of your existing Next.js application:

```bash
pnpm add @lingva/core @lingva/react @lingva/next
pnpm add --save-dev --allow-build=@lingva/cli @lingva/cli
pnpm lingva init --mode local --no-auth --sdk next
pnpm lingva check
```

The command creates portable `lingva.config.yaml`, a typed adapter at
`.lingva/generated/runtime.ts`, local translation files, the generated project,
and a provider wrapper. It does not create a Next.js application, install the
SDK packages, or add the bundled starter's package scripts.

## What It Covers {#what-it-covers}

The bundled repository example covers:

- local-first `lingva.config.ts` (the init scaffold instead owns portable YAML)
- `.lingva/translations/{locale}.json`
- `.lingva/generated/project.ts`
- `createLingvaNextProvider` from `@lingva/next`
- `LingvaText`, `useTranslation`, and `useLocale`
- `.lingva/metadata.json` for warning-free key metadata validation
- Next.js App Router provider mounting in `app/layout.tsx`
- local verification through `verify:starter` and `lingva check`

Run its package scripts from the monorepo root:

```bash
pnpm --filter @lingva/example-next-starter verify:starter
pnpm --filter @lingva/example-next-starter lingva:check
pnpm --filter @lingva/example-next-starter dev
```

## Scaffold Equivalent {#scaffold-equivalent}

For an existing Next.js app with the packages installed, initialize local mode:

```bash
pnpm lingva init --mode local --no-auth --sdk next
```

Then mount the generated `AppLingvaProvider` from `src/lingva/provider.tsx` in
your App Router layout. The generated adapter imports the runtime from
`.lingva/generated/runtime.ts`; it does not require a root TypeScript config.

When you add default-locale keys, refresh metadata before CI:

```bash
pnpm lingva metadata lingva.config.yaml --output .lingva/metadata.json
pnpm lingva metadata lingva.config.yaml --check
pnpm lingva check
```

For the bundled repository example, metadata commands instead target its existing
`lingva.config.ts`. The `verify:starter` and hosted helper scripts belong to that
example and are not emitted by `init`.

## Hosted Delivery Later {#hosted-delivery-later}

The starter intentionally begins in local mode. Once your project is ready for
hosted delivery, open `/app/projects/<project-id>` and copy values from **Consumer
application setup**. For the bundled example, run from the monorepo root:

```bash
cp examples/next-starter/.env.example examples/next-starter/.env.local
pnpm --filter @lingva/example-next-starter verify:hosted-env
```

That checker reads the example's environment files, verifies required setup
values, and rejects every Lingva `NEXT_PUBLIC_*` variable whose name contains
`TOKEN`, `KEY`, or `SECRET`. It is a conservative setup check, not a test of
remote connectivity or key permissions. A read-only browser SDK key needs a
separately reviewed browser configuration.

Generate a no-mutation publish plan before calling hosted services:

```bash
pnpm --filter @lingva/example-next-starter lingva:plan
```

The starter script runs local `manifest` and `bundle` commands for `en` and
`ru`, writing artifacts to `.lingva/artifacts/plan` without hosted requests or
locale-file edits. Update the script if you change the locale list. `push` and
`publish` with a configured endpoint are not dry runs.

When hosted delivery is ready, copy the complete login command and publish URL
from that setup panel. These commands run the bundled example's CLI and scripts
from the monorepo root:

```bash
pnpm --filter @lingva/example-next-starter exec lingva auth login
# Stage: pnpm --filter @lingva/example-next-starter exec lingva auth login --platform-url https://stage.lingva.dev
export LINGVA_PUBLISH_API_URL="<copy publish URL from Lingva>"
pnpm --filter @lingva/example-next-starter lingva:push
```

The CLI does not automatically load `.env.local`; export the publish URL as
shown or pass it with `--api-url`. To refresh the bundled example's locale files,
run `pnpm --filter @lingva/example-next-starter exec lingva pull --api-url "$LINGVA_PUBLISH_API_URL"`.
In a customer application, invoke `pnpm lingva push` or `pnpm lingva pull` directly
with that application's config and publish URL; the starter script names are not
built-in CLI commands.

After publishing, verify the current locale bundle through the environment's
delivery URL with the generated read-scoped SDK key. Publishing alone does not
switch the starter from local delivery; configure its hosted delivery mode and
bundle URL separately.

The generated `delivery:read` SDK key may be used by the browser runtime. Keep
authoring, publishing, administration, and service credentials server-side; do
not expose those private values through `NEXT_PUBLIC_*` variables.
