# Микрофронтенды

Используйте один проект Lingva как контракт переводов, а каждому микрофронтенду
предоставьте собственную среду выполнения. Это изолирует состояние фреймворков
и не связывает независимо развёрнутые приложения друг с другом.

## Рекомендуемая структура {#recommended-layout}

```text
packages/i18n/
  lingva.config.yaml
  .lingva/generated/runtime.ts
  .lingva/translations/{locale}.json
  .lingva/generated/project.ts
apps/
  shell/
  account-react/
  billing-angular/
  help-vue/
```

Экспортируйте сгенерированный проект из общего пакета. Затем каждый микрофронтенд
создаёт собственный адаптер фреймворка на основе этого проекта и конфигурации.

```ts
import { createLingvaJsRuntime } from '@lingva/js';
import { lingvaConfig, lingvaProject } from '@example/i18n';

export const lingva = createLingvaJsRuntime({
  ...lingvaConfig,
  project: lingvaProject,
});
```

Используйте подходящий пакет на границе каждого фреймворка:

| Фреймворк | Пакет             | Граница приложения              |
| --------- | ----------------- | ------------------------------- |
| React     | `@lingva/react`   | `<LingvaProvider config={...}>` |
| Angular   | `@lingva/angular` | `provideLingvaAngular(...)`     |
| Vue       | `@lingva/vue`     | `app.use(createLingvaVue(...))` |
| Svelte    | `@lingva/svelte`  | `createLingvaSvelte(...)`       |
| Vanilla   | `@lingva/js`      | `createLingvaJsRuntime(...)`    |

Все эти адаптеры используют один сгенерированный тип ресурсов и контракт доставки
среды выполнения. Поэтому код конкретного фреймворка остаётся внутри каждого
микрофронтенда без дублирования логики загрузки локалей или отмены запросов.

Не используйте один изменяемый экземпляр среды выполнения в изолированных
развёртываниях. Разделяйте контракт переводов и передавайте выбранную локаль явно.

## Передача локали {#locale-propagation}

Для микрофронтендов на одной странице используйте событие приложения, содержащее
проверенную локаль Lingva. Для изоляции через iframe передавайте локаль в URL
iframe или через типизированный контракт `postMessage`. Дочернее приложение
отвечает за вызов метода переключения локали своего адаптера. При удалённой
доставке в обычном JS дождитесь `runtime.loadLocale(locale)`: этот метод и выбирает,
и загружает локаль. Последующий вызов `runtime.setLocale(locale)` создаёт новый клиент
и теряет состояние загруженного клиента. Angular, Vue и Svelte предоставляют
асинхронные методы `setLocale`; React переключает состояние синхронно и загружает
удалённые переводы в эффекте провайдера. Отображайте состояния загрузки и ошибки
каждого адаптера. При использовании `postMessage` проверяйте источник сообщения
и содержимое, а при отправке явно задавайте целевой источник.

```ts
const childUrl = new URL('/account/', window.location.origin);
childUrl.searchParams.set('locale', selectedLocale);
iframe.src = childUrl.toString();
```

Относитесь к передаче локали как к любому публичному контракту интеграции:

- отклоняйте локали, которые дочернее приложение не поддерживает;
- используйте одинаковую резервную локаль во всех приложениях;
- развёртывайте совместимые ключи перевода до кода, которому они нужны;
- отображайте локальный индикатор загрузки, пока загружается удалённый набор переводов локали.

## Проверка в CI {#ci-verification}

Запускайте `lingva sync --check` и `lingva check` один раз для общего пакета переводов,
затем собирайте всех потребителей. Полный пример также должен проверять работу
каждого независимо обслуживаемого приложения во всех поддерживаемых локалях.
