# Python

[`lingva-sdk`](https://pypi.org/project/lingva-sdk/) предоставляет среду выполнения
переводов Lingva для серверных сервисов, фоновых задач и приложений на Python.
Отдельный пакет `lingva-cli` предоставляет команды для работы с переводами в
репозитории, запуская общий движок на Rust. Оба поддерживают Python 3.9 и новее.

У пакетов разные задачи:

- `lingva-cli`: тонкая обёртка для запуска самостоятельной команды `lingva` на Rust
- `lingva-sdk`: `LingvaClient` для чтения проверенных пакетов локалей в коде Python

SDK 0.1.5, содержащий только среду выполнения, и CLI 0.1.5 устанавливаются и
выпускаются независимо. Ранние версии SDK включали обёртку запуска CLI;
обновите их перед установкой отдельного CLI.

## Установка {#install}

Установите среду выполнения и необязательный асинхронный HTTP-клиент:

```bash
python -m pip install "lingva-sdk[http]"
python -m pip install lingva-cli
```

Используйте `python -m pip install lingva-sdk`, если достаточно синхронной
доставки. В рабочем окружении закрепите совместимую версию, поскольку SDK Python
пока находится на ранней стадии выпуска:

```text
lingva-sdk[http]==0.1.5
lingva-cli==0.1.5
```

Если вы обновляете старую установку SDK, которой принадлежит консольная команда
`lingva`, сначала обновите SDK, затем переустановите CLI:

```bash
python -m pip install --upgrade "lingva-sdk[http]==0.1.5"
python -m pip install --force-reinstall "lingva-cli==0.1.5"
```

Такой порядок не даёт удалению старого SDK убрать консольную команду нового CLI.
Конфигурация, переводы, учётные данные и состояние на платформе не требуют
миграции данных.

Отдельная консольная команда CLI при первом запуске скачивает двоичный файл Rust
закреплённой версии и проверяет его контрольную сумму. Для этого нужен доступ к
сети. Выполните `lingva --version`, чтобы заранее загрузить исполняемый файл перед
автономной работой. Последующим локальным командам подключение к платформе не
нужно. CLI никогда не переключается на реализацию команд в Python. Задавайте
`LINGVA_CLI_BINARY` только при разработке и в тестах, когда намеренно проверяете
локально собранный движок. Проверка контрольной суммы обеспечивает целостность
относительно скачанного файла контрольных сумм; доверие к источнику распространения
по-прежнему необходимо.

В [полном справочнике CLI](./cli.md) описаны все 23 клиентские команды,
поддерживаемые параметры, создание выходных файлов, извлечение ключей из исходного
кода и особые случаи.

## Создание переносимой конфигурации проекта {#create-the-portable-project-config}

Запускайте CLI из корня клиентского репозитория. По умолчанию используется
удалённый режим платформы; для него достаточно один раз войти через браузер:

```bash
lingva auth login
lingva init --sdk python
```

Если у учётной записи один проект, он выбирается автоматически. Если проектов
несколько, выберите один в терминале или передайте `--project-id`. Lingva
заполнит идентификатор проекта, локали, окружение и адрес API данными платформы.

Команда создаёт `lingva.config.yaml` и файлы локалей в
`.lingva/translations/`. YAML-файл содержит тот же переносимый контракт CLI,
который используют интеграции JavaScript и CI:

```yaml
projectId: my-service
environment: dev
locales:
  - en
  - ru
defaultLocale: en
fallbackLocale: en
translationFiles: .lingva/translations/{locale}.json
apiUrl: https://your-lingva-api.example
apiKeyEnv: LINGVA_API_KEY
```

Для полностью локальной доставки явно отключите аутентификацию на платформе.
Учётная запись Lingva и ключ проекта не требуются. После установки или
предварительной загрузки исполняемого файла локальная работа также не требует
доступа к сети:

```bash
lingva init --sdk python --mode local --no-auth
```

```yaml
projectId: my-service
environment: dev
locales:
  - en
  - ru
defaultLocale: en
fallbackLocale: en
translationFiles: .lingva/translations/{locale}.json
```

## Аутентификация команд платформы {#authenticate-hosted-commands}

Локальные `sync` и `check` не требуют учётной записи. Для `pull` и `push`,
работающих с платформой, скопируйте API-ключ проекта или параметры входа через
браузер из раздела **Consumer application setup** на странице проекта Lingva.
Сохраните ключ проекта один раз:

```bash
lingva auth use-key --api-key "$LINGVA_API_KEY" --project-id my-service
lingva auth status
```

Вход через браузер с OAuth находит правильного издателя и клиента для выбранного
окружения:

```bash
lingva auth login
# Stage: lingva auth login --platform-url https://stage.lingva.dev
```

Учётные данные сохраняются с ограниченными правами доступа в
`~/.lingva/credentials.json`. Все установочные адаптеры CLI используют этот
общий файл, только если не указан явный токен и нет настроенного ключа из
переменной окружения. Выполните `lingva auth logout`, чтобы удалить сохранённые
данные. `lingva --help` показывает все команды, а вывод `lingva --version`
пригодится при обращении в поддержку.

Запустите `lingva update` через адаптер Python, чтобы проверить стабильную версию
`lingva-cli` на PyPI. Команда показывает команду обновления пакета Python с
закреплённой версией, но сама обновление не выполняет. `--channel` переопределяет
автоматически определённый способ установки.

Загрузите переводы из репозитория непосредственно в приложение:

```python
from lingva import LingvaClient

client = LingvaClient.from_config(locale="ru")
print(client.t("welcome.title", name="Yury"))
```

Ключи с вариантами используют тот же контракт выбора, что и среды выполнения
JavaScript. Выбирайте по идентификатору варианта или метаданным; если селектор
неизвестен, используется первый вариант:

```python
print(client.t("marketing.hero.title", variant="bold", name="Yury"))
print(client.t("marketing.hero.title", variant={"tone": "warm"}, name="Yury"))
```

`from_config` читает файлы, созданные `lingva init`, создаёт проверенный пакет
переводов в памяти и применяет `fallbackLocale`. Передавайте
`config_file="path/to/lingva.config.yaml"` только если процесс запускается не из
корня репозитория.

Аргумент конфигурации необязателен для `sync`, `check`, `pull` и `push`. По
умолчанию каждая команда ищет `lingva.config.yaml` в корне текущего проекта.

## Согласование переводов в репозитории {#keep-repository-translations-aligned}

Используйте `sync` после добавления ключей в локаль по умолчанию. Существующие
переводы никогда не перезаписываются:

```bash
lingva sync
```

`sync` никогда не обращается к платформе Lingva. Команда только согласует
локальные файлы локалей и структуру вариантов. `pull` скачивает переводы с
платформы; `push` отправляет локальные переводы.

Синхронизация сохраняет переведённый текст вариантов, согласуя идентификаторы и
метаданные (`tone`, `mood`, `intonation`, `label` и `context`) с локалью по
умолчанию. Повторяющиеся идентификаторы и недопустимые нетекстовые конечные
значения не проходят проверку.

Передача данных платформе защищена от конфликтов. `pull` выполняет трёхстороннее
слияние на основе последнего снимка платформы в `.lingva/remote-state.json`.
Независимые локальные изменения и изменения ключей на платформе объединяются.
Если ключ изменён с обеих сторон, команда останавливается без перезаписи
локального файла. `push` отправляет последнюю полученную ревизию публикации.
Платформа возвращает HTTP `409`, если после этой ревизии кто-то уже выполнил
публикацию.

Файл состояния относится к конкретной машине и исключён через gitignore.
Первая отправка предполагает пустой проект на платформе. Если в проекте уже
есть публикация, отправка отклоняется, пока вы не выполните `lingva pull`.
Используйте `lingva push --force` только для намеренного восстановления по
принципу «последняя запись побеждает». Повторная отправка тех же данных после
успешного выполнения идемпотентна.

Используйте параметры командной строки, когда CI передаёт значения вместо
записи в конфигурацию:

```bash
lingva pull --api-url "$LINGVA_PUBLISH_API_URL" --auth-token "$LINGVA_API_KEY"
lingva push --api-url "$LINGVA_PUBLISH_API_URL" --auth-token "$LINGVA_API_KEY" --invalidate
```

В CI используйте проверку, которая не изменяет файлы:

```bash
lingva check
```

Команда объединяет проверку согласованности схемы с проверкой переводов,
вариантов, метаданных и рабочих процессов. Она завершается с ненулевым кодом,
если структура расходится или нарушается настроенная политика проверки, в том
числе при недопустимых ключах переводов. Правила именования описаны в разделе
[Конфигурация](./configuration.md#translation-key-contract).

Python и движок Rust соблюдают общий переносимый контракт ключей длиной до 200
символов: латинские буквы ASCII, цифры, точки, подчёркивания и дефисы; первый
символ — буква или цифра; точки не могут идти подряд или стоять в конце.
Вложенные ключи разворачиваются по тому же контракту, а совпадающие пути,
записанные через точки и вложенность, недопустимы.

## Подключение проекта на платформе {#connect-a-hosted-project}

Откройте проект Lingva и разверните **Consumer application setup**:

1. выберите **Python** как целевую интеграцию
2. создайте SDK-ключ проекта и скопируйте его значение, показанное один раз
3. скопируйте адрес API, идентификатор проекта, окружение и сформированные параметры пакета переводов
4. сохраните ключ в `LINGVA_API_KEY`; никогда не добавляйте его в коммит

Страница проекта формирует значения для выбранного окружения. Источник каждого
значения указан явно:

| Значение         | Где получить                                                       |
| ---------------- | ------------------------------------------------------------------ |
| `projectId`      | Заголовок проекта или сформированный фрагмент `lingva.config.yaml` |
| `environment`    | Переключатель окружения доставки проекта                           |
| `apiUrl`         | Руководство Python в **Consumer application setup**                |
| `LINGVA_API_KEY` | Токен, показанный один раз после создания SDK-ключа проекта        |

Получите текущие переводы с платформы в репозиторий:

```bash
export LINGVA_API_KEY='<project-sdk-key>'
lingva pull
```

Опубликуйте локальные файлы переводов, если ключ имеет право записи:

```bash
lingva check
lingva push
```

Для доставки в приложение используйте ключ только для чтения, а для публикации
из CI — отдельный ключ с правом записи. Храните ключи в серверной части
клиентского приложения или в хранилище секретов CI, а не в браузерных или
мобильных сборках.

## Загрузка переводов с платформы в Python {#load-hosted-translations-in-python}

```python
import asyncio
import os

from lingva import LingvaClient, LingvaDeliveryTarget

target = LingvaDeliveryTarget(
    base_url="https://your-lingva-api.example",
    project_id="my-service",
    environment="dev",
    api_key=os.environ["LINGVA_API_KEY"],
)


async def main() -> None:
    client = await LingvaClient.from_url(
        target,
        locale="ru",
        fallback_locale="en",
    )
    print(client.t("welcome.title", name="Yury"))


asyncio.run(main())
```

Для синхронных сервисов используйте `LingvaClient.from_url_sync(...)`. Оба
загрузчика проверяют пакет переводов перед его использованием и сохраняют
поведение поиска ключей и подстановки переменных согласованным с другими средами
выполнения Lingva.

## Получение переводов через GitHub Actions {#github-actions-pull-hook}

CLI работает без интерактивного ввода и может обновлять переводы в репозитории
после ручного или внешнего запуска:

```yaml
name: Pull Lingva translations

on:
  workflow_dispatch:
  repository_dispatch:
    types: [lingva-translations-updated]

jobs:
  pull:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: '3.13'
      - run: python -m pip install lingva-sdk lingva-cli
      - run: lingva pull
        env:
          LINGVA_API_KEY: ${{ secrets.LINGVA_API_KEY }}
```

Добавьте принятую в репозитории автоматизацию веток или pull request после
`lingva pull`. Lingva намеренно не выбирает политику слияния за клиента.
