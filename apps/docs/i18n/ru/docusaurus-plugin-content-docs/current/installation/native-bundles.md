# Предварительные версии нативных SDK

Lingva включает предварительные версии клиентов Swift, Kotlin и Flutter в
исходном коде. Все они используют один публичный контракт пакетов локалей и
реализуют точный поиск ключей, выбор вариантов по идентификатору или метаданным,
подстановку объявленных переменных, проверку схемы и сохранение последнего
корректного пакета переводов. Они ещё не опубликованы в реестрах соответствующих
экосистем, поэтому используйте их как локальные зависимости, пока API проходят
проверку.

Python распространяется отдельно через PyPI. Для `lingva-sdk`, переносимой
синхронизации CLI и доставки с платформы используйте отдельное
**[руководство по Python](./python.md)**.

## Контракт пакета переводов {#bundle-contract}

`lingva publish` записывает манифест и по одному пакету переводов для каждой
выбранной локали. Пакет локали содержит вычисленные плоские сообщения вместе с
информацией об их происхождении, переменных и метаданных:

```json
{
  "schemaVersion": 1,
  "projectId": "mobile-app",
  "environment": "dev",
  "locale": "en",
  "defaultLocale": "en",
  "fallbackLocale": "en",
  "generatedAt": "2026-09-25T00:00:00.000Z",
  "keyCount": 1,
  "fallbackKeys": [],
  "messages": {
    "welcome.title": "Welcome, {name}."
  },
  "variants": {
    "welcome.title": [
      { "id": "warm", "text": "Welcome, {name}.", "tone": "warm" },
      { "id": "bold", "text": "Ship it, {name}!", "tone": "direct" }
    ]
  },
  "sources": {
    "welcome.title": "en"
  },
  "variables": {
    "welcome.title": ["name"]
  },
  "entries": [
    {
      "key": "welcome.title",
      "value": "Welcome, {name}.",
      "sourceLocale": "en",
      "fallback": false,
      "variables": ["name"],
      "namespace": "welcome"
    }
  ]
}
```

`schemaVersion` задаёт границу совместимости. Предварительные версии клиентов
отклоняют неизвестные версии, а не принимают потенциально несовместимый пакет.

Для создания локальных выходных файлов:

```bash
pnpm add --save-dev --allow-build=@lingva/cli @lingva/cli
```

Сначала экспортируйте проект без адресов сервисов, чтобы создать локальные файлы:

```bash
pnpm lingva export lingva.config.yaml --format json --output .lingva/artifacts/project.json
pnpm lingva publish .lingva/artifacts/project.json \
  --locale en,ru \
  --output-dir .lingva/artifacts/publish
```

Скопируйте пакеты локалей в ресурсы нативной сборки. Доставка с платформы Lingva
требует аутентификации; методы обновления предварительных версий Swift, Kotlin
и Flutter сейчас не добавляют учётные данные. Для обновлений по сети поставьте
серверный или пограничный обработчик с аутентификацией перед Lingva и отдавайте
только пакеты, которые авторизованное приложение вправе читать.

Экспорт не включает адреса сервисов и учётные данные. Не добавляйте `--api-url`
или переопределение `--config` с адресом платформы при создании локальных файлов.
Обычный `publish` с конфигурацией, содержащей адрес сервиса, отправляет данные;
каталог вывода не является параметром пробного запуска.

## Предварительные пакеты {#preview-packages}

Исходные пакеты находятся в репозитории:

- `sdks/swift` — библиотека Swift Package Manager с именем `Lingva`
- `sdks/kotlin` — библиотека JVM в пространстве имён `dev.lingva`
- `sdks/flutter` — пакет Flutter с именем `lingva_flutter`

Каждая предварительная версия предоставляет модель пакета переводов,
переводчик и хранилище или контроллер, который заменяет текущее состояние только
после декодирования и проверки новых данных. Общий тестовый набор в
`sdks/fixtures` помогает сохранять согласованное поведение.

### Swift {#swift}

Добавьте `sdks/swift` как локальный пакет Swift и используйте продукт `Lingva`:

```swift
import Lingva

let store = LingvaBundleStore()
let bundle = try await store.refresh(from: bundleURL)
let title = bundle.translate("welcome.title", variables: ["name": "Yury"])
let boldTitle = bundle.translate(
    "welcome.title",
    variables: ["name": "Yury"],
    variant: .id("bold")
)
```

`refresh(from:)` по умолчанию не отправляет учётные данные Lingva и ожидает
успешный HTTP-ответ. Для удалённой загрузки используйте прокси с аутентификацией
под контролем клиента; данные упакованного вместе с приложением пакета загружайте
через `load(data:)`. Прямой адрес доставки платформы, требующий ключ проекта,
не будет работать без настройки аутентифицированных запросов.

### Kotlin {#kotlin}

Пока пакет находится на предварительной стадии, подключите `sdks/kotlin` как
локальную сборку Gradle:

```kotlin
val store = LingvaBundleStore()
val bundle = store.refresh(bundleUri)
val title = bundle.translate("welcome.title", mapOf("name" to "Yury"))
val warmTitle = bundle.translate(
    "welcome.title",
    variant = LingvaVariantSelector.Metadata(mapOf("tone" to "warm")),
)
```

Выполняйте синхронный сетевой вызов из корутины IO или слоя репозитория;
предварительная версия намеренно не выбирает область корутин за приложение.
`refresh` не добавляет ключ Lingva; направляйте сетевые запросы через доверенный
сервер или поставляйте проверенный пакет переводов вместе с приложением.

### Flutter {#flutter}

Подключите `sdks/flutter` как зависимость по пути, затем разместите управление
контроллером рядом с состоянием локали приложения:

```dart
final lingva = LingvaBundleController();
await lingva.refresh(bundleUri);
final title = lingva.translate(
  'welcome.title',
  values: {'name': 'Yury'},
  variant: const LingvaVariantSelector.id('bold'),
);
```

`LingvaBundleController` является `ChangeNotifier`; успешная загрузка отправляет
одно уведомление, а неудачная оставляет предыдущий пакет переводов без изменений.
Предварительная версия не добавляет учётные данные Lingva, поэтому обновление
с платформы требует прокси с аутентификацией под контролем клиента.

## Обязанности загрузчика {#reader-responsibilities}

Минимальный загрузчик должен:

1. декодировать и проверять пакет переводов перед передачей интерфейсу
2. искать точные плоские ключи в `messages`
3. выбирать варианты по идентификатору или метаданным и использовать первый вариант, если совпадение не найдено
4. заменять только переменные, объявленные для этого сообщения
5. предсказуемо использовать резервное значение, когда ключ или пакет недоступен
6. кешировать удалённые пакеты и сохранять последнюю корректную версию

Не встраивайте ключи администрирования проекта или токены публикации в
распространяемое нативное приложение. Текущая доставка с платформы требует
аутентификации; используйте SDK-ключ только для чтения лишь на доверенном сервере
или получайте данные через собственный пограничный обработчик с аутентификацией.
Изменения данных остаются серверными операциями.

Правила множественного числа, форматированные сообщения, подписи, постоянные
кеши и политики фонового обновления ещё не стандартизированы. Пока эти контракты
не определены, оставляйте особенности жизненного цикла приложения и политику
постоянного хранения вне предварительного клиента.
